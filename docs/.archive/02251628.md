`tsc --noEmit` 报出 5 个错误，意味着当前代码库无法通过类型检查。

| 4 | `src/extension-content.ts` | 201 | `msg` 参数隐式 `any`（TS7006）。`browser.runtime.onMessage.addListener((msg)` 缺少类型注解。 |

- #5: 在 `src/` 下新建 `vite-env.d.ts`，声明 `declare module '*.css?inline' { const css: string; export default css; }`。

```typescript
import { BUILTIN_TEMPLATES } from './core/builtin-templates.generated';

async function getTemplateBlob(id: string): Promise<ArrayBuffer | undefined> {
  if (id.startsWith('builtin-')) {
    const tpl = BUILTIN_TEMPLATES[id];
    if (!tpl) return undefined;
    const bin = atob(tpl.data);
    const buf = new Uint8Array(bin.length);

    return buf.buffer;
  }
  // ...existing custom template logic
```

## ~~P0-3 扩展版未使用本地 pandoc.wasm~~

`PLAN-full.md §7.3` 明确要求：

> 扩展环境使用 `browser.runtime.getURL('pandoc.wasm')` → fetch → ArrayBuffer

但 `extension-background.ts` 硬编码了 CDN URL：

```typescript
const PANDOC_WASM_URL =
  'https://pandoc.org/app/pandoc.wasm?sha1=2ab8055eb0803168da93d4b784fe40aa06551dfa';
```

`bin/pandoc.wasm`（58 MB）虽然存在于项目中，但扩展构建并未将其打包，background 也未通过 `browser.runtime.getURL()` 加载它。

**后果：**
- 扩展版仍依赖外部 CDN，离线不可用。
- 违背 PLAN 中"扩展内置 Pandoc，无需配置"的设计意图。
- Chrome manifest 的 `web_accessible_resources` 未包含 `pandoc.wasm`。

**建议修复方式：**

1. 在 `vite.config.ts` 扩展构建中，将 `bin/pandoc.wasm` 复制到 `dist/extension/` 输出目录。
2. Chrome manifest 的 `web_accessible_resources` 添加 `pandoc.wasm`。
3. `extension-background.ts` 改为：
   ```typescript
   const wasmUrl = browser.runtime.getURL('pandoc.wasm');
   const resp = await fetch(wasmUrl);
   wasmCache = await resp.arrayBuffer();
   ```

## ~~P0-4 油猴模式 Web Worker 创建方式错误~~

`userscript.ts` 中：

```typescript
const workerUrl = new URL('./core/pandoc.worker.ts', import.meta.url);
await initPandoc(wasmBytes, workerUrl);
```

油猴脚本构建为 IIFE 单文件（`lib.formats: ['iife']`），`import.meta.url` 在 IIFE 中不可用或指向宿主页面 URL，`new URL(relative, base)` 无法解析到打包后的 worker 代码。

**后果：** Worker 创建失败，Pandoc 初始化失败，整个导出功能不可用。

**建议修复方式：**

利用 Vite 的 `?worker&inline` 或手动内联 worker：

```typescript
// 方案 A: Vite inline worker
import PandocWorker from './core/pandoc.worker.ts?worker&inline';
const worker = new PandocWorker();

// 方案 B: Blob URL
const workerCode = `/* 构建时内联的 worker 代码 */`;
const blob = new Blob([workerCode], { type: 'application/javascript' });
const workerUrl = URL.createObjectURL(blob);
```

需要同步调整 `converter.ts` 的 `initPandoc()` 签名，或在 userscript 入口处直接构造 Worker 实例传入。

## ~~P1-1 内置模板元数据硬编码且不完整~~

`userscript.ts` 和 `extension-content.ts` 中各自定义了：

```typescript
const builtinTemplates: TemplateMeta[] = [
  { id: 'builtin-gb', name: 'GB/T 标准格式', isBuiltin: true, description: '...' },

```

但 `builtin-templates.generated.ts` 实际生成了 **3 个模板**：`builtin-gb`、`builtin-academic`、`builtin-minimal`。

```typescript
  ([id, t]) => ({ id, name: t.name, isBuiltin: true, description: t.description })
);
```

## ~~P1-2 模板管理 / 配置逻辑重复（DRY 违反）~~

`userscript.ts` 和 `extension-content.ts` 各自独立实现了完全相同的逻辑：

- `loadConfig()` / `saveConfigPartial()`
- `getTemplateList()` / `uploadTemplate()` / `deleteTemplate()` / `getTemplateBlob()`
- `createCallbacks()` — 两个文件内容几乎一字不差

**后果：** 任何模板/配置相关的 bug 修复或功能变更，必须同步修改两个文件。一旦遗忘，两个入口行为将产生分歧。

**建议：** 抽取一个 `src/core/storage-helpers.ts`，接收 `IStorage` 实例，导出所有配置/模板管理函数。两个入口点只负责构造 `IStorage` 实例后传入。这不违反 PLAN 中"Storage 归 apps"的原则——存储适配器仍在入口文件，但 **使用存储的业务逻辑** 应共享。

## ~~P1-4 DeepSeek DOM 选择器脆弱~~

`deepseek.ts` 中用于定位消息工具栏的选择器：

```typescript
const toolbars = document.querySelectorAll(
  'div.ds-scroll-area div.ds-flex:not(:has(div.ds-flex))',
);
```

以及分享对话框的选择器依赖 `.ds-atom-button.ds-basic-button--primary` 和 `innerText.includes('创建分享链接')`。

**风险：**
- DeepSeek 任何一次前端重构都可能导致选择器失效。
- `div.ds-flex:not(:has(div.ds-flex))` 可能匹配到非工具栏的嵌套 flex 元素，导致误注入。
- `:has()` 选择器在旧版浏览器中不可用（Chrome 105+, Firefox 121+）。

**建议：**
- 增加更具特征的上下文匹配（例如检查最近的消息气泡容器再向下查找工具栏）。
- 提取选择器为常量，集中管理，便于 DeepSeek UI 变更时快速修改。
- 增加 `try-catch` 保护和注入失败的 console.warn 日志。


## ~~P1-5 配置变更无防抖，每次按键都写入存储~~

`panel-settings.ts` 中模板编辑器直接绑定 `input` 事件：

```typescript
prefixTextarea = createTextarea({
  label: '文档前缀（document prefix）',
  rows: 5,
  onChange: (v) => {
    config.documentPrefix = v;
    cb.onConfigChange({ documentPrefix: v });
  },
});
```

每次键入字符都调用 `onConfigChange` → `GM_setValue` / `browser.storage.local.set`。

**后果：**
- 油猴模式下可能触发频繁的同步写入；
- 扩展模式下 `browser.storage.local.set` 是异步的但高频调用仍不理想；
- 网络使用 IndexedDB-backed storage 时可能产生可感知的卡顿。

**建议：** 在 `createTextarea` 的 `onChange` 或 `panel-settings.ts` 中加 300-500ms debounce。
